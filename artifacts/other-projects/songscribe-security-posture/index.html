SongScribe Security Posture

A review of the kuuza-ai/songscribe codebase at the line level, the regulatory obligations it already carries, and the gap between where it is today and what a technical due-diligence team would expect to find.

ScopeBranch dev @ 206f916, full repository
MethodSource review, SCA, secret scan, licence audit
Findings2 critical · 8 high · 9 medium · 7 low
Not doneNo pen test, no live environment, no cloud config review

1. Executive summary

SongScribe's application security is better than typical for a seven-month-old product built by one engineer, and materially worse than what any acquirer, enterprise customer or regulator will expect. Those two statements are both true and they explain the shape of this report.

The good part is deliberate, not accidental. Row-level security is on for every table. Money movements are idempotent with dedupe keys and database-level advisory locks. Webhooks verify signatures. Secrets are compared in constant time. Audio sits in a private bucket behind signed URLs. The retention cron fails closed. Several migrations exist for no purpose other than revoking dangerous grants that Supabase hands out by default, and two of the four end-to-end tests were written after real security incidents, which tells you the team learns from its mistakes.

The bad part is structural. There is no Content-Security-Policy, no HSTS, no error tracking, no alerting, no audit log, no admin interface, no dependency update process and no security contact. The framework is running two unauthenticated remote-code-execution advisories. Thirty-four of the fifty-nine privileged database functions omit the one line that prevents search-path hijacking. And the entire product depends on an unofficial reseller of an API that its upstream vendor does not publish, which is simultaneously the biggest security, legal and commercial risk in the business.

On compliance, three obligations are live today and unmet: Nigerian data-controller registration, EU AI Act Article 50 content marking (in force since 2 August 2026), and the PCI DSS script-integrity requirements that a hosted Stripe checkout does not outsource. A fourth, the treatment of voice conversations as biometric-adjacent personal data, is a question the privacy policy does not currently answer at all.

On acquisition, the single most valuable thing you can do this quarter has nothing to do with code: confirm in writing that the company owns the copyright in the code its sole author wrote. Everything else on the diligence list is fixable in weeks. A missing IP assignment is fixable only with the cooperation of a person whose leverage grows the moment a term sheet exists.

3. Technical findings

Each finding names the file so you can open it. Severity is my judgement of likelihood multiplied by impact for this product at this stage, not a CVSS score.

Critical

SEC-01Critical

Two unauthenticated remote-code-execution advisories in the installed Next.js

package.json pins Next.js 16.0.0. That version is inside the affected range for two advisories that require no authentication: a remote code execution on Windows-hosted servers, and a remote code execution in the image optimisation endpoint when AVIF files are processed. The app uses next/image heavily, with remote patterns allowing Supabase storage, the R2 samples bucket and provider CDNs, so the image pipeline is reachable and actively used.

Vercel's managed runtime is Linux, which removes the Windows vector for production, but not for any self-hosted or preview environment, and not for the image path at all.

FixUpgrade to Next.js 16.3.5 or later. It is outside the currently declared range, so it needs a version bump and a regression pass over the App Router surfaces, not just npm audit fix. Do this before anything else in this document.
Where: package.json · confirmed by npm audit --omit=dev on 22 Sep 2026 · GHSA-p293-qw3h-jr36, GHSA-2xp9-vwfh-vxw4
SEC-02Critical

The full source, including the internal architecture guide, is on a public GitHub repository

The mirror at github.com/neo1415/songscribe was public when the branches were pushed on 14 September. It carries every branch, and with them claude.md — a 912-line document describing the architecture, the flows, the known gotchas and where the security controls live. No secrets are in the repository, which is the one saving grace, but this is a complete map for an attacker and a complete blueprint for a competitor.

It also complicates the acquisition story. A buyer asking "has the source ever been publicly disclosed" now has a yes, with a date range, and will want to know for how long and who cloned it.

FixMake the repository private today. Then assume disclosure: rotate every credential referenced anywhere in the repo's history or documentation, even placeholders, and record the exposure window in the incident log you are about to start keeping.
Where: github.com/neo1415/songscribe · verified public 14 Sep 2026 · status today unconfirmed

High

SEC-03High

No Content-Security-Policy anywhere

buildSecurityHeaders() sets X-Frame-Options, X-Content-Type-Options, Referrer-Policy, X-DNS-Prefetch-Control and Permissions-Policy. There is no Content-Security-Policy and no Strict-Transport-Security.

That matters more here than on an average site because the pages load Google Tag Manager and a Meta pixel, both of which inject further scripts at runtime. Any cross-site scripting flaw — in a song title, a shared-page title, a lyric rendered as markup, a third-party tag that gets compromised — has no second line of defence. It is also the control that PCI DSS 4.0.1 requirements 6.4.3 and 11.6.1 are effectively asking you to demonstrate, and those two requirements are not outsourced by using Stripe's hosted checkout.

FixAdd a CSP in report-only mode first, tune it against real traffic for a week, then enforce. Add HSTS with a long max-age once you are certain every subdomain is HTTPS. Both go in src/lib/security-headers.ts, which already has the right shape for per-route overrides.
Where: src/lib/security-headers.ts · next.config.ts · src/app/layout.tsx (GTM-KP63F74M, Meta pixel 750371207831007 are hardcoded literals)
SEC-04High

34 of 59 privileged database functions do not pin their search path

The schema defines 59 SECURITY DEFINER functions — functions that run with the definer's privileges rather than the caller's — and only 25 include SET search_path. A definer function without a pinned search path is the classic PostgreSQL privilege-escalation primitive: a caller who can create objects in a schema that appears earlier on the search path can shadow a table or function name the definer body references, and have their own code run with elevated privileges.

On Supabase the practical exposure is narrower than on a self-managed cluster, because authenticated cannot normally create objects in public. It is still the single most repeated hardening miss in the schema, it is what every database security scanner will flag first, and the newer migrations show the author already knows the pattern — the credits functions written in August all pin it, the February ones do not.

FixOne migration adding SET search_path = public, pg_temp to every definer function that lacks it. Mechanical, low risk, and it closes an entire finding class in a single review.
Where: supabase/migrations — 59 security definer declarations, 25 set search_path. Worst concentrated in 001_initial_schema.sql and the Feb 2026 files.
SEC-05High

The Flutterwave webhook binds a payment to an account by email address

The primary path is sound: verify the verif-hash header, re-verify the transaction against Flutterwave's API, check status and amount, dedupe on flw_<id>. Then, if no pending order matches, the handler looks the user up by the customer email Flutterwave reported and can create an active order for them.

Email is not an identity in this system. A customer who pays from a different email than their account gets nothing; two accounts sharing a billing email get each other's entitlements; and anyone who can cause a payment to carry a chosen email influences which account is credited. It is an authorisation decision made on an attacker-influenceable, non-unique attribute.

FixBind strictly on tx_ref. When there is no match, record the payment in a reconciliation queue, alert, and stop. Never create an order from a fallback lookup.
Where: src/app/api/webhooks/flutterwave/route.ts — .eq('email', customerEmail) at ~line 133, order insert at ~line 201
SEC-06High

Flutterwave's verif-hash is a static shared secret, and the amount comparison is not currency-aware

Two issues in one place. First, verifyWebhookSignature compares the verif-hash header against a configured secret in constant time, which is exactly what Flutterwave's own documentation asks for — but that header is a fixed value, identical on every webhook, not an HMAC over the request body. It is a bearer token, so anyone who observes one legitimate webhook can replay arbitrary bodies. The code largely defuses this by re-verifying every transaction against the Flutterwave API before acting, which is the right defence and deserves credit. The residual risk is that any future branch which trusts the payload without that round trip silently becomes forgeable.

Second, the order path stores amount_cents: Math.round(amount * 100). The codebase has a currency-aware toMinorUnits helper and imports it in the same file, but this branch does not use it. Today Flutterwave means naira, which happens to have two decimal places, so the number is right by luck rather than by construction.

FixKeep the verify-then-settle discipline and write it down as a rule for future branches. Replace both Math.round(amount * 100) call sites with toMinorUnits(amount, currency).
Where: src/lib/flutterwave.ts:104 · src/app/api/webhooks/flutterwave/route.ts:185, :207
SEC-07High

The music provider callback is authenticated by a secret in the query string

buildCallbackUrl appends ?secret=… to the webhook URL, and verifyCallback compares it in constant time. Query strings are the worst place to carry a credential: they land in access logs, proxy logs, referrer headers and error reports at every hop between the provider and Vercel. The provider's own dashboard will display it.

The design is not naive — when verification fails, the handler does not reject outright, it polls the provider for the task's real status over an authenticated channel and only then acts, which means a forged callback cannot fabricate a completed song. That is genuinely good. But it also means a missing or rotated secret degrades to the slow path silently, with nothing but a console.info to say so.

FixMove the secret to a request header if the provider supports one, and alert on any unverified callback rather than only logging it. The polling fallback should be the exception you get paged about, not the quiet default.
Where: src/lib/music/callback-url.ts:20 · src/lib/music/providers/musicapi.ts:182 · src/lib/music/callback-handler.ts:155
SEC-08High

Rate-limit identity trusts the first hop of x-forwarded-for

getIdentifier() falls back for anonymous callers to headers.get('x-forwarded-for')?.split(',')[0]. The left-most entry of that header is the value the client sent, not the value the edge observed. On Vercel this is normally rewritten, but the code does not depend on that being true, and the moment anything else sits in front of the app — a WAF, Cloudflare, a self-hosted deployment — an attacker sets the header and gets a fresh quota bucket per request.

Every anonymous control in the product keys off this: the demo generation limit, the lyrics limit, the audio streaming limit, the contact form.

FixPrefer x-vercel-forwarded-for (or the right-most non-proxy entry) and treat a missing trustworthy value as unidentified rather than as 127.0.0.1, which currently pools every such caller into one shared bucket.
Where: src/lib/rate-limit.ts — getIdentifier()
SEC-09High

Redis failure behaviour is inconsistent across the three systems that depend on it

I checked each one rather than assuming, and they disagree:

  • Rate limiting has no error handling at all. An Upstash outage makes limiter.limit() throw, which surfaces as a 500 from every protected route. That is fail-closed, which is safe, but it means Redis is a hard dependency for the whole API.
  • Music dispatch capacity catches and returns true — fail-open. During an outage there is no in-flight ceiling on provider spend.
  • Producer admission catches and returns {ok:false, reason:'unavailable'} — fail-closed.

Three behaviours for one dependency is a decision that was never made. Worth noting this corrects my own earlier handover note, which described the whole system as failing open.

FixDecide deliberately per control, document it in one place, and alert on the degraded path. My recommendation: fail closed for anything that spends money, fail open for anything that only affects experience.
Where: src/lib/rate-limit.ts (no catch) · src/lib/music/budget.ts:141 (return true) · src/lib/producer/session-budget.ts:225 (return {ok:false})
SEC-10High

No error tracking, no alerting, no audit trail

Observability is console.log with structured prefixes, read through Vercel's log viewer. There is no error tracker, no metric, and nothing that pages a human. Concretely, nobody would learn that a webhook signature started failing, that the music provider is being struck out for health, that credit spends are erroring, or that someone is walking ids across the audio proxy.

Separately, there is no audit log for privileged actions. Tier grants, announcements and credit backfills all run as the service role from a laptop, and the only record is the row they changed. For an incident review, and for any future SOC 2 attempt, that is not enough.

FixAdd a Sentry-class tracker and three alerts to start: webhook verification failures, provider health strikes, and errors from the credits RPCs. Add an audit_log table that every service-role script and future admin action writes to.
Where: whole codebase · no error-reporting dependency in package.json

Medium

SEC-11Medium

The image proxy performs no authorisation at all

/api/images takes a path parameter, checks only that it begins with covers/, mints a one-hour signed URL with the service role and redirects. There is no session check, no ownership check and no rate limit. Anyone who learns or guesses a path can read any cover image in the bucket, and the one-hour signed URL can then be shared onwards freely.

Impact is bounded because cover art is generated artwork rather than intimate content, and paths embed UUIDs so they are not enumerable. It is still an unauthenticated read against private storage, and it is the kind of finding a diligence reviewer circles immediately.

FixResolve the path back to a song, then apply the same three-way ownership check the audio route already implements (owner, valid share token, or matching demo session). Shorten the signed URL life and add the stream rate limiter.
Where: src/app/api/images/route.ts — compare with src/app/api/audio/stream/route.ts, which does this correctly
SEC-12Medium

Personal data is written to application logs

The audio proxy logs user ids, owner ids and demo session ids on every unauthorised attempt. The Flutterwave webhook logs the customer's email address when a lookup fails. Producer routes log session ids. None of this is unusual engineering practice, and all of it is personal data flowing into a third-party log store with no stated retention period, no access control of its own, and no mention in the privacy policy.

FixRedact or hash identifiers in logs, set a retention period on the log platform, and name log processing in the privacy policy. Under both NDPA and GDPR, logs are processing like any other.
Where: src/app/api/audio/stream/route.ts (several) · src/app/api/webhooks/flutterwave/route.ts:137
SEC-13Medium

The service-role key is used on developer laptops

scripts/announce.mjs and scripts/backfill-credits.mjs both require SUPABASE_SECRET_KEY — the credential that bypasses every RLS policy in the schema. The announce script's own header comment identifies this as the most dangerous credential in the system and proposes moving it into a manual CI job. That has not happened.

Both scripts are unusually well guarded against the accident case: production requires an explicit --confirm-production flag, dry runs are the default, and the backfill aborts rather than trimming an implausible grant. Neither guards against the laptop case.

FixMove both to manual CI jobs so the key lives in CI secrets and every run has an actor and a timestamp. Rotate the key afterwards.
Where: scripts/announce.mjs · scripts/backfill-credits.mjs
SEC-14Medium

Demo quota is a check-then-update race

Carried over from the handover review and repeated here because it has a cost line. The route reads demo_usage, decides, then updates. Parallel requests from one IP all pass the read. The comment in the file acknowledges it as acceptable for a soft cap. It is a soft cap on a hard cost: every extra generation is a real payment to the music provider for an anonymous user.

FixOne SQL function that increments and refuses atomically, in the pattern check_style_boost_quota already uses.
Where: src/app/api/generate/route.ts:112
SEC-15Medium

No dependency update process, and three more advisories waiting

Beyond the Next.js criticals, the audit reports a high in sharp (libheif), a high in nanoid, a high in brace-expansion, plus development-only advisories in vitest and js-yaml. Nothing in the repository updates dependencies on a schedule: no Dependabot config, no Renovate, and GitLab's dependency-scanning template is not among the two security templates the pipeline includes.

FixAdd GitLab Dependency Scanning to .gitlab-ci.yml alongside the SAST and secret-detection templates already there, and turn on automated update merge requests.
Where: .gitlab-ci.yml · package-lock.json · 8 advisories total on 22 Sep 2026
SEC-16Medium

The CSRF defence depends on one environment variable being exactly right

proxy.ts rejects any mutating /api/* request whose Origin or Referer does not match NEXT_PUBLIC_APP_URL, defaulting to http://localhost:3000. The logic is correct and the webhook paths are properly exempt. The fragility is operational: if that variable is unset or wrong in an environment, every write silently 403s, and if it were ever set to something permissive the protection quietly disappears. There is no startup assertion.

Note also that accepting Referer as a fallback is weaker than Origin alone, since referrer policies vary by browser and can be suppressed.

FixAssert the variable at boot and fail to start without it in production. Prefer Origin; treat a missing Origin on a same-site fetch as a rejection rather than reaching for Referer.
Where: src/proxy.ts — CSRF block at the top of proxy()
SEC-17Medium

The admin gate exists, is unused, and is enforced in the wrong layer

proxy.ts redirects anyone without profiles.role = 'admin' away from /admin. No /admin route exists yet, so nothing is protected today. The concern is what happens when someone builds one: middleware-level authorisation is a routing convenience, not a security boundary, and it does nothing for /api/admin/* handlers, which are not covered by that check at all.

Relatedly, is_admin() is deliberately left executable by anon — a choice the migration comments explain and which is defensible, since it reads auth.uid() and returns a boolean about the caller themselves.

FixWhen the admin surface lands, check the role inside every handler and enforce it again in RLS policies. Treat the middleware redirect as user experience only.
Where: src/proxy.ts:93-106 · supabase/migrations/20260130200000_fix_profiles_rls_recursion.sql
SEC-18Medium

Prompt injection is structurally contained, but not defended in the prompt

I looked for this specifically because the AI Producer hands user text to a model that can call tools. The architecture is genuinely good: the six tools only ever propose, spending requires a one-time nonce bound to a hash of the brief, the nonce expires in 120 seconds, the tool loop is capped at three iterations, and prompt-builder.ts runs user fields through a sanitize() helper. A user who injects instructions can make the agent say odd things; they cannot make it spend money without the human pressing the confirm card.

What is missing is any instruction in the 229-line system prompt telling the model that user content is data rather than instruction, and any output handling for the case where a model returns attacker-chosen text that is then rendered. The containment is entirely structural, with no depth behind it.

FixAdd an explicit boundary statement to the system prompt, and keep the structural guarantees as the real defence — they are the part that works.
Where: src/lib/producer/system-prompt.ts · src/lib/producer/tool-runtime.ts · src/lib/prompt-builder.ts
SEC-19Medium

No documented backup, restore or incident process

Supabase takes automated backups on paid plans, but nothing in the repository states the retention, whether a restore has ever been tested, who declares an incident, or how a breach notification would be issued inside the 72 hours that GDPR requires. For an audio product, the storage bucket matters as much as the database, and bucket contents are not covered by a Postgres backup.

FixWrite a one-page runbook: backup scope and retention, a tested restore, key rotation steps, and an incident path with named roles and regulator deadlines. Test the restore once and date it.
Where: no runbook, no SECURITY.md, no incident policy in the repository

4. What is already strong

A security report that lists only problems gives a false picture, and in diligence you will be asked what the controls are. These are real and defensible.

RLS everywhereEvery table has row-level security enabled, with a documented fix for the recursive policy bug that bit profiles early on. Definer functions closedForty-seven revoke statements across the migrations, several in migrations whose entire purpose is closing grants Supabase adds by default. Three separate hardening passes in March and September. Idempotent moneyDedupe keys on every ledger row, advisory locks inside spend_credits, one settlement function shared by webhook and redirect, verify-then-settle for Flutterwave, Stripe signature verification. Constant-time comparisonsafeEqual is used for the cron secret, the Flutterwave hash, the music callback secret and the producer session token. Consistently, not occasionally. Private mediaBoth storage buckets are private. Audio is served through a proxy that checks ownership, share token or demo session before minting a 60-second signed URL. Voice session bindingAn HMAC token over {userId, sessionId}, minted only where ownership was just checked. It closed a real vulnerability where a caller could name someone else's producer session and have the agent read out their brief. Cron fails closedThe retention endpoint returns 404 — not 401 — when unauthenticated, and refuses to run at all when CRON_SECRET is unset. Security in CIGitLab SAST and secret detection run on every pipeline; typecheck, lint, format and 1,413 unit tests block merges. Tests written from incidentse2e/spend.spec.ts exists because both spend routes once answered anonymous callers. The test's header documents the exact flaw. That is the right instinct.

5. Compliance

SongScribe sells to Nigeria, the UK and the euro area, processes intimate personal data, takes card payments, records voice, and generates synthetic audio. That combination pulls in six regimes at once. None of them are satisfied today, and three of them are already in force.

Nigeria Data Protection Act 2023

The NDPA creates a category called a data controller or processor of major importance, and the Commission's guidance puts you in it once you process the personal data of more than 200 data subjects. SongScribe holds accounts, emails, payment references, song briefs naming real people, and play history. Two hundred users is an early milestone, not a distant one, and the obligation attaches whether or not anyone has registered.

What that means concretely: register with the NDPC, file a Compliance Assessment Report annually, notify the Commission of significant changes within 60 days, and appoint a Data Protection Officer. The General Application and Implementation Directive issued in March 2025 is the operative detail. Penalties for a controller of major importance run to ₦10 million or 2% of annual gross revenue, whichever is higher.

There is no evidence in the codebase or the legal pages of any of this. The privacy policy mentions "third-party" twice and does not name a single processor.

GDPR and UK GDPR

Pricing in GBP and EUR, with prices held in product_prices for both, is the textbook indicator of "targeting" under Article 3(2). Extraterritorial scope applies. The gaps, in the order a regulator would find them:

  • No named subprocessors. Users are not told that their song brief goes to a music provider in one jurisdiction, their lyrics to Google, their conversation to Google or Anthropic, their voice to ElevenLabs, their email to Resend and ZeptoMail, their payment to Stripe or Flutterwave. Each of those needs naming, a lawful basis, and a data processing agreement on file.
  • No records of processing, no DPIA. A DPIA is expected for large-scale processing involving novel technology; an AI system that generates content from personal stories and records voice is squarely in that territory.
  • No data subject request process. Account deletion exists and is thorough — it soft-deletes rows, deletes the auth user and clears cookies. There is no export, and no documented route for access, rectification or objection requests.
  • International transfers. Nigerian, US and EU processing all mix. Transfer mechanisms need to be identified per processor.
  • Breach notification. Seventy-two hours, and currently nobody is monitoring for a breach at all (SEC-10), so the clock would start whenever someone happened to notice.

Voice and biometric-adjacent data

This one is under-appreciated in the current design. The AI Producer's voice mode streams the user's microphone to ElevenLabs. Voice recordings are personal data always, and under most GDPR readings they become biometric data — an Article 9 special category requiring explicit consent — when processed for the purpose of identifying a person. SongScribe does not identify anyone by voice, which is the strongest argument that Article 9 is not engaged. But the conservative reading, and the one a buyer's counsel will take, is that a voice conversation carrying a person's story about their family needs explicit notice, a stated retention period, and a signed DPA with the processor.

Today, a user taps a microphone button, the browser asks for permission, and nothing tells them a third-party US company receives the audio. ElevenLabs publishes a DPA, operates under the EU-US Data Privacy Framework and offers data residency, but residency is an enterprise-tier feature and processing may still occur outside the selected region for support and moderation. Their stated biometric retention is until no longer needed or three years after the relationship ends.

Minimum viable fix: a sentence at the microphone prompt naming ElevenLabs and linking the policy, ElevenLabs' DPA countersigned and filed, the retention period written into the privacy policy, and a decision recorded on whether voice is stored at all or only streamed. If it is only streamed and never persisted, say so — that is the strongest position available and it is nearly free.

EU AI Act, Article 50

This is the finding with the nearest deadline, because the deadline has passed. Article 50's transparency obligations applied from 2 August 2026. SongScribe is a deployer of a generative AI system and, because it packages and supplies generated audio to end users under its own brand, plausibly a downstream provider too.

Two obligations bite. Providers of systems generating synthetic audio must mark outputs in a machine-readable format so they can be detected as artificially generated. Deployers publishing AI-generated content must disclose its artificial nature to the audience. Fines reach €15 million or 3% of worldwide turnover.

SongScribe does neither. The MP3 that a customer downloads carries no provenance metadata, the public share page at /s/[token] does not state that the track is AI-generated, and the licence PDF is silent on it. The marketing copy says "AI-powered", which is a claim about the service, not a disclosure attached to the content.

What good looks like here is cheap. Write C2PA-style provenance or, at minimum, ID3 tags naming the generator into every file at the point storage.ts saves it. Add a visible line on the share page and in the licence certificate. Adopt the DDEX AI-disclosure fields in any distribution metadata. This is a few days of work that converts a live regulatory exposure into a feature you can advertise, and it aligns with where Spotify and Apple Music have already moved.

PCI DSS

Both payment flows redirect to a hosted page — Stripe Checkout Sessions and Flutterwave payment links — and no card data ever touches SongScribe's servers. That is the right architecture and it puts you in SAQ A, the shortest self-assessment.

SAQ A is not zero. Under PCI DSS 4.0.1, merchants retain requirements 6.4.3 (inventory and authorise every script on the payment page) and 11.6.1 (detect tampering with payment page headers and content), plus the Requirement 12 policy obligations. With no CSP (SEC-03), no script inventory, and Tag Manager free to inject arbitrary scripts into pages in the payment flow, there is currently no way to evidence either. Eligibility for SAQ A also has to be confirmed with the acquirer rather than assumed.

Copyright, licensing and the supply chain

Three problems stack here, and together they are the most commercially serious section of this report.

The output may not be copyrightable. The US Copyright Office's position, as set out in its 2025 guidance on generative AI, is that purely AI-generated material is not protected; registration requires meaningful human authorship, and typing a prompt and pressing generate does not qualify. A SongScribe user who fills in a wizard and receives a track has, on that reading, no copyright to be granted. Yet the Exclusive tier sells "full commercial rights", "Content ID allowed" and "Exclusive Worldwide license", and the FAQ says the song "will never be resold or reused by us". Some of that is a contractual promise SongScribe can keep. "You own it and can register it with Content ID" is not.

The FAQ promises features that do not exist. It states that higher tiers provide lossless WAV downloads. Nothing in the codebase produces WAV. There is a audio.wav row in the credit price list, which suggests intent, but the download path serves MP3. That is a straightforward misrepresentation to fix before it becomes a refund dispute.

The supply chain is the existential one. As of 2026 Suno publishes no sanctioned developer API. Every "Suno API" in circulation, including sunoapi.org and musicapi.org, wraps reverse-engineered access. SongScribe's entire product is built on one of them. Three consequences: the service can stop the day Suno blocks the reseller; the commercial-use rights the reseller passes through may not be the reseller's to grant, which undermines every licence SongScribe sells downstream; and an acquirer's counsel will treat this as a material risk requiring either a direct vendor agreement or a demonstrated ability to switch providers.

The provider abstraction in src/lib/music/ was built for exactly this. Finishing it — a second adapter, and routing stems, cover art and style boost through the seam rather than calling sunoClient directly — is the single highest-value engineering task in the business, and it should be framed to the team as risk reduction rather than refactoring.

6. Acquisition readiness

A buyer's technical diligence asks four questions: do you own it, does it work, is it safe, and can someone else run it. Here is how SongScribe answers today.

Deal killers, in order

ACQ-01Critical

Chain of title on the code

Every one of the 258 commits is by one author. If there is no signed agreement assigning copyright in that work to the company — an employment contract with an IP clause, or a contractor IP assignment — then the company does not clearly own its only asset. This is the most common reason small software acquisitions collapse, and it is the only item on this list whose difficulty increases with time and with the existence of a deal.

Do nowConfirm the agreement exists and covers all work from the first commit. If it does not, get one signed while the relationship is good and nothing is pending. Do the same for anyone else who has ever contributed, including designers who produced the Figma files the UI is built from.
ACQ-02Critical

No contract with the upstream model provider

See the supply-chain paragraph above. A buyer will ask to see the agreement that entitles SongScribe to generate and commercially license music. There is a reseller relationship, and the reseller's own right to grant that is unclear. Expect either a price reduction, an escrow holdback, or a condition precedent requiring a direct agreement.

Do nowObtain the reseller's written terms on commercial use and sublicensing. Approach Suno or an alternative vendor about a direct agreement. Finish the provider seam so "we can switch in a week" is demonstrable rather than aspirational.
ACQ-03High

Bus factor of one, with no operational documentation

One author, no code review history, no runbook, no architecture document that is current (claude.md is stale and README.md is create-next-app boilerplate), and every privileged operation performed by hand from a laptop. Buyers price key-person risk directly, and integration planning depends on being able to hand the system to a new team.

Do nowThe handover handbook is the start. Add a runbook, put reviews on merge requests, and get a second engineer's hands on every critical path. You taking over is itself the mitigation — make the transfer visible in the commit history.
ACQ-04High

No security or privacy programme to point at

No penetration test, no SOC 2, no ISO 27001, no vulnerability disclosure policy, no incident history, no access review, no evidence of offboarding. For a consumer product at this stage that is normal; the problem is that "normal" still scores zero on a diligence questionnaire, and enterprise customers ask the same questions before they sign.

Do nowCheapest credible order: fix the findings in this report, write the policies, commission a one-week external penetration test, then start a SOC 2 Type I. Type II needs an observation window, so it is a next-year item.

8. Method and limits

This review read the source of the dev branch at commit 206f916: every API route, the proxy, the security headers, the rate limiter, the Supabase clients, the payment and music webhooks, the media proxies, the producer session and token code, and all 57 migrations. It ran a software composition analysis and licence inventory over 267 production dependencies, a secret scan across the full git history for Stripe, Flutterwave, Supabase, Google and Resend key patterns, and a survey of current guidance on the six regulatory regimes above.

What it did not do, and what a real assessment would add: no penetration test and no dynamic testing against a running instance; no review of the Supabase, Vercel, Upstash or Cloudflare account configuration, which is where multi-factor authentication, access lists and backup settings actually live; no review of the RLS policies executing against real data, which is the only way to prove they hold; no phishing or social-engineering assessment; and no legal opinion — the compliance section identifies obligations and gaps, and a qualified lawyer in each jurisdiction should confirm the conclusions before they are acted on commercially.
