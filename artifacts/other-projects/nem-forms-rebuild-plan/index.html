1 · Claims lifecycle: REPORT → PAY

Your reading is right: FNOL and submission are the same event here. The claim form is the report of loss, so REPORT completes the moment a claim form is accepted and a ticket number is issued. No two-part form.

REPORTReport the loss · Claim registered · Claim number issuedAutomatic on submit
SUBMITSubmit required documents · Complete requirements · Complete claim fileCustomer + claims unit
REVIEWConfirm policy coverage · Assess loss & quantum · Proceed / declineClaims unit
ACCEPTReceive settlement offer · Accept or query · Revised offer possible · DischargeCustomer decides
PAYPayment processed · Payment confirmed · Claim closedFinance / claims

Data model

Today "status" is one string (pending / processing / approved / rejected) written by four different endpoints with three different field schemas, and the admin viewer bypasses the API and writes Firestore directly. That all goes. Each claim document gains one structured block:

claim: {
  stage: 'report' | 'submit' | 'review' | 'accept' | 'pay' | 'closed' | 'declined',
  step:  'registered' | 'docs_requested' | 'docs_complete' | 'coverage_confirmed'
       | 'assessed' | 'offer_issued' | 'offer_queried' | 'offer_revised'
       | 'discharged' | 'paid' | 'payment_confirmed' | 'closed',
  waitingOn: 'customer' | 'nem',
  history: [{ stage, step, at, byUid, byName, note, customerVisible }],
  outstandingDocuments: [{ key, label, required, receivedAt?, url? }],
  offers: [{ version, amount, currency, basis, excess, deductions, issuedAt,
             status: 'offered'|'accepted'|'queried'|'superseded', dvUrl?, queryReason? }],
  decision?: { outcome: 'proceed'|'decline', reason, at, byUid },
  payment?: { reference, amount, paidAt, confirmedAt },
  notifiedAt, targetDate            // 60-day clock, see section 5
}
status: 'pending'|'processing'|'approved'|'rejected'   // kept, derived from stage

The legacy status field stays and is derived from the stage, so every existing table, badge and email keeps working while the new UI lands. Compliance forms (KYC, CDD, NFIU) keep their simple status model; this block is claims-only.

One endpoint, one dialog, one email

  • Backend: POST /api/claims/:collection/:id/transition with { step, note, offer?, outstandingDocuments?, decision?, payment? }. It validates the allowed transition, appends history, derives stage and legacy status, enforces assignedClaimCollections scoping for claims staff, logs the audit event, and sends the one stage email. The four current status routes are retired behind it.
  • Customer endpoints: POST .../offer/:version/accept, POST .../offer/:version/query (reason required, optional new evidence), and the existing documents upload route for outstanding documents.
  • Admin UI: the Processing / Approved / Rejected buttons in FormViewer become a single "Move claim" dialog that shows only the legal next steps, requires a note, and requires a written reason on decline. A "Request documents" checklist and an "Issue offer" form live in the same dialog.
  • Emails: one template, stage-specific copy, deep-linking to the customer's claim page. Replaces the four near-identical HTML bodies that exist now.
  • Customer view: a ClaimProgress component: the five-step rail, "waiting on you / waiting on NEM", the outstanding-documents checklist with upload, the offer card with Accept and Query, and the dated history.

2 · Submit-first accounts

The client's ask: no registration form. A guest fills the form, gives an email in a small modal, submits, and receives two emails: the submission confirmation and their login details with a generated 8-character password that they must change on first sign-in.

What already exists and gets reused

  • server-utils/passwordGenerator.cjs generates and validates passwords (currently minimum 12).
  • server-utils/emailTemplates.cjs has a welcome email with temporary password and login link.
  • users/{uid}.mustChangePassword plus PasswordResetGuard and /auth/password-reset already force a change on first login, but only for admin-created users.
  • The two submit hooks already park a pending submission in session storage and resume it after sign-in.

The flow

  1. Guest reaches the summary step. Instead of redirecting to sign-in, an EmailCaptureModal asks for email, full name and phone. If the email already has an account the modal switches to a password field, because we must not attach a submission to someone else's account on the strength of an email address alone.
  2. POST /api/submit-form accepts unauthenticated submissions carrying guest: { email, name, phone }. In one transaction the backend creates the Firebase user with a generated password, writes users and userroles with mustChangePassword: true and temporaryPasswordExpiresAt, writes the submission with the new UID, and returns the ticket.
  3. Two emails go out: confirmation with the ticket, and credentials. They are separate so the password never sits next to the claim details.
  4. First sign-in lands on the forced password change. Login with an expired temporary password is refused with a one-click "resend credentials" that is rate-limited per email.
  5. Sign-up shrinks to name, email, password for people who want an account first. Broker sign-up stays as is.
Password length. NIST allows system-generated passwords as short as 6 characters if they are random and short-lived. Eight is fine only if the credential expires within 24 hours, is single-use, is never logged, and the forced change is enforced server-side. If NEM is open to it, the cleaner option is a "set your password" link (Firebase reset link, 1-hour expiry, single-use) instead of a password in email. I'll build the temporary password unless you say otherwise, and it will be 8 characters as requested.

Session fix rides along

The account work touches the same code paths as the open critical issue, so the fix lands here: /api/login and /api/exchange-token issue a random 256-bit session id stored in a sessions collection mapped to the UID; requireAuth stops accepting a bare UID from the cookie or the Bearer header. The frontend keeps sending whatever it receives as sessionToken, so only two admin pages that read it from local storage need adjusting.

4 · Dashboards: claims for claims, compliance for compliance

Customer

  • The six analytics tiles (total, KYC, claims, pending, approved, rejected, approval rate) go. The header shows exactly what the client asked for: number of claims and the progress of each active claim as a compact rail.
  • Below that, four tabs: Claims · KYC · CDD · NFIU. Each lists that type's submissions with status and date; the claims tab opens the claim page with the full tracker.
  • The customer form viewer is rebuilt in the same component library as the dashboard (shadcn + Tailwind). Today it is the only customer page built in MUI, which is why it looks foreign.

Staff

  • The backend already distinguishes claims and compliance roles. The admin sidebar does not: a claims officer sees KYC tables and vice versa. Navigation and route guards become role-scoped: claims staff see a claims queue grouped by stage and their assigned claim types; compliance staff see KYC, CDD and NFIU only; admins and super admins see both.
  • A claims queue view sorted by "days since notification" so the 60-day clock is visible before it is breached.

5 · Money, offers and regulation

Short answer on pricing: this portal never collects payment. Claims pay out, and compliance forms are free. There is nothing to price. What the industry does show is the settlement offer, and Nigerian practice already discloses the amount on the discharge voucher before payment, so showing it in the portal changes nothing legally.

  • Show: offer amount, basis (sum insured, excess, deductions), the discharge voucher as a download, payment reference once paid.
  • Query flow: the customer can accept or query an offer with a reason and new evidence; NEM issues a revised offer as a new version. History is kept per version, which is exactly the "revised offer may be sent" line in the claims department's table.
  • Regulation: the Nigerian Insurance Industry Reform Act 2025 requires settlement within 60 days of notification and a written reason for any decline, with a fine plus compound interest for late payment. Secondary sources disagree on when the clock pauses for missing documents, so every stage transition is timestamped and "documents requested" is an explicit step. That gives NEM the evidence either way. Legal should confirm the reading; I couldn't get the Act's text.
  • Document checklists per claim type (motor, fire, burglary, marine, GPA and so on) come from config, mirroring what NSIA, Cornerstone and NEM's own motor guide publish.
